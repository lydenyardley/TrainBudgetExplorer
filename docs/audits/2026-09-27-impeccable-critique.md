itself the reason several findings below are gone:

## Design specificity verdict

**The station experience is authored around a real product thesis, and the route system now matches it.** The earlier verdict named one largest weakness: the seam between the single-origin and all-origin outputs, where a station page could offer navigation to pages its build had not published, and where the deployment's root was a station page while the product's route model put a chooser there. That seam is closed — one route contract, a manifest of the pages actually written, a link crawl that refuses to publish a site with a dangling internal link, and a release manifest that is proved against the files on disk.

The route seam stayed shut through two later passes. The local runner no longer deletes the page a single-origin build wrote — it removes only the folders this build's own manifest does not name — and the default fare set is the reviewed one the brief promises rather than the broader set that sat behind it. What is still not settled is the one the route work never was: the deployed site publishes a single station, and a reader arriving at a “where can we go from anywhere” product meets exactly one origin.

The privacy page is no longer visually generic in the one way the detector caught — the brand line above an oversized "Privacy" heading is gone — but the contact text is still plain text, so the route still reads as a document rather than a page. The honesty work is better placed than it was: provenance and freshness sit beside the prices, the notice's practice list is generated from the build rather than restated, and the decision-critical caveats the first pass found buried now sit above the results.

### Cognitive load and emotional journey

- **Chooser:** low-to-moderate load, unchanged. Budget and station search are the two decisions, the 40-result cap is disclosed, and the page now says what its ranking is *not* — destination count, not busyness, not proximity. A reader who knows their town but not the station's exact name or code still has no natural way in, and the code-prefix match is the only new help (C27).
- **Station page:** moderate-to-low load, improved on a phone. The budget and the results are the first screen; ticket type, party and destination type fold behind one control that states what is currently narrowed, so the reader can change the budget with one hand and reach results without scrolling past a control wall. On a desktop the layout is unchanged.
- **Privacy:** low reading load, slightly improved. The eyebrow and oversized heading are gone and the practice list gained a plain-language entry, but the contact is still plain text.
- **Emotional arc:** the price question and the named origin land immediately, and the reader now has a way to keep and hand off a shortlist rather than remembering a list. Both dips the first pass named are closed: a restricted fare now states in the feed's own words what it is valid on, and the cost of the ticket button is stated above the rows rather than discovered after the click. The button names its destination, the copy and times panels no longer displace one another, the freshness line and the per-row "no service on this date" wording remove two more.

## What is working

1. **The price-first premise is immediately legible.** The budget sits inside the main question rather than being buried in a form, which is the clearest expression of the product's differentiator.
2. **Several hard states are genuinely designed, not merely tolerated.** Empty ticket modes clear stale results and explain alternatives; unpriced origins are distinguished from prices outside the budget; a missing journey now says which of three absences it is; no-match station searches name the failed query and a recovery; a result set that changed under the reader returns to its first page.
3. **The route contract is now one contract.** Chooser, station and privacy exist in both build modes, every internal link in the built artifact is crawled and must resolve, and the release's routes are written down and proved.
4. **The interface takes trust and keyboard interaction seriously.** Price provenance and freshness sit beside the results, rows use real table markup, the origin picker uses links and returns focus on Escape, row actions have enlarged hit areas, and the search state lives in the address.

### P2 — Significant usability, coverage, and accessibility issues

**C27 — P2 | The chooser requires a known station name or a code prefix.** *(partly addressed)*  
**Status:** open, narrowed — the limitation is now stated on the page; the capability gap is unchanged.  
**Routes:** full-build root chooser.  
**Evidence:** matching is by name substring or three-letter code prefix, and the first 40 matches are ranked by number of destinations. `PRODUCT.md` correctly notes that the fares location records contain no coordinates or region. New since the first pass: the chooser says what its order is and is not — "Ordered by how many destinations this download prices from each station — not by how busy it is, and not by how near it is" — and a no-match names the three-letter code route, so a reader is no longer left guessing what a code is for. No geographic lookup exists, and the audit still holds that "nearest" is not derivable from this feed.  
**Impact:** a first-time traveller who knows where they live but not the official station name or code still has no natural way to choose an origin; a high destination count is not a "near me" signal.  
**Action:** keep the stated limitation, and treat an opt-in geographic lookup as a separate decision with a named, reviewed data source and a manual-search fallback — not as an inference from this feed.

## Questions to carry into a future design pass

1. ~~Is the release meant to expose the full station network now, or intentionally just Grantham?~~ **Partly answered:** the route contract no longer depends on the answer, and the deployment publishes a one-station chooser whose contract is the same as a full build's. What is still open is the coverage decision — a one-station release is coherent, but a reader arriving at a "where can we go from anywhere" product meets one origin.
2. ~~Should the product default to "up to £X" (inclusive) or strictly "under £X"?~~ **Answered: "up to £X".** The budget is worded inclusively, and one resolver drives the heading, the title and every shared link, so the figure and the wording cannot drift apart again.
3. Is a Two Together price meant to be shown only for a two-adult party, or as an explicitly conditional per-person comparison? Now enforced in code (the solo case is refused rather than shown), so the remaining question is whether the enforcement is the answer the brief wanted.
4. ~~Which information must be visible before a click: seller handoff, date basis, fare restriction, and commission disclosure?~~ **Answered, and acted on:** all four are now above the results — the handoff and the commission as paragraphs above the table, the date basis in the freshness line, and the fare's validity on the row itself. The method accordion keeps only the calculation detail.
5. Does the local preview keep its own build step, or does `run.py` become a server for a folder the builder produces? The concrete cost of that split has been fixed, so the question is open again rather than answered by a defect: the runner still shells out to the builder, which works, and no finding says it should not.
