## Design specificity verdict

**The station experience is authored around a real product thesis, and the route system now matches it.** The earlier verdict named one largest weakness: the seam between the single-origin and all-origin outputs, where a station page could offer navigation to pages its build had not published, and where the deployment's root was a station page while the product's route model put a chooser there. That seam is closed — one route contract, a manifest of the pages actually written, a link crawl that refuses to publish a site with a dangling internal link, and a release manifest that is proved against the files on disk.

The route seam stayed shut through two later passes. The local runner no longer deletes the page a single-origin build wrote — it removes only the folders this build's own manifest does not name (C31) — and the default fare set is the reviewed one the brief promises rather than the broader set that sat behind it (C07). What is still not settled is the one the route work never was: the deployed site publishes a single station, and a reader arriving at a “where can we go from anywhere” product meets exactly one origin.

The privacy page is no longer visually generic in the one way the detector caught — the brand line above an oversized "Privacy" heading is gone — but the contact text is still plain text, so the route still reads as a document rather than a page. The honesty work is better placed than it was — provenance and freshness sit beside the prices, and the notice's practice list is generated from the build rather than restated — but some decision-critical ticket-link and timetable caveats still live in a closed methodology disclosure (C03, C04).

### Cognitive load and emotional journey

- **Chooser:** low-to-moderate load, unchanged. Budget and station search are the two decisions, the 40-result cap is disclosed, and the page now says what its ranking is *not* — destination count, not busyness, not proximity. A reader who knows their town but not the station's exact name or code still has no natural way in, and the code-prefix match is the only new help (C27).
- **Station page:** moderate-to-low load, improved on a phone. The budget and the results are the first screen; ticket type, party and destination type fold behind one control that states what is currently narrowed, so the reader can change the budget with one hand and reach results without scrolling past a control wall. On a desktop the layout is unchanged.
- **Privacy:** low reading load, slightly improved. The eyebrow and oversized heading are gone and the practice list gained a plain-language entry, but the contact is still plain text.
- **Emotional arc:** the price question and the named origin land immediately, and the reader now has a way to keep and hand off a shortlist rather than remembering a list. Confidence still dips at the two places the first pass named: an unexplained fare condition on the row, and a ticket button that opens a seller search whose cost is only explained in a closed disclosure (C03) u2014 though the button now names its destination, and the copy/times panels no longer displace one another. The new freshness line and the per-row "no service on this date" wording remove two more dips.

## What is working

1. **The price-first premise is immediately legible.** The budget sits inside the main question rather than being buried in a form, which is the clearest expression of the product's differentiator.
2. **Several hard states are genuinely designed, not merely tolerated.** Empty ticket modes clear stale results and explain alternatives; unpriced origins are distinguished from prices outside the budget; a missing journey now says which of three absences it is; no-match station searches name the failed query and a recovery; a result set that changed under the reader returns to its first page.
3. **The route contract is now one contract.** Chooser, station and privacy exist in both build modes, every internal link in the built artifact is crawled and must resolve, and the release's routes are written down and proved.
4. **The interface takes trust and keyboard interaction seriously.** Price provenance and freshness sit beside the results, rows use real table markup, the origin picker uses links and returns focus on Escape, row actions have enlarged hit areas, and the search state lives in the address.

### P1 — Release and trust blockers

**C01 — P1 | The automated public deployment bypasses the unresolved licence gate.**  
**Status:** open — re-verified; unchanged.  
**Routes:** any deployed fares/station page.  
**Evidence:** `docs/publish-checklist.md` still marks confirmation of the DTD account entitlement and current public-use/attribution terms as incomplete (30 unchecked boxes, 6 checked; the DTD row reads "must be confirmed"). The same checklist says not to publish until those answers are verified. `.github/workflows/deploy.yml` still downloads DTD feeds and deploys on pushes to `main` and on a daily schedule once credentials are present; it supplies attribution text but has no approval or licence-clearance gate. The build now refuses a public release that carries no notice or no privacy contact, which is adjacent but is not a licence decision.  
**Impact:** a technically successful build can publish licensed fares while the project's own release condition remains unresolved.  
**Action:** require an explicit, reviewable release approval after the licence checklist is completed (and keep the build capable of testing locally without that approval); do not treat attribution wording as proof of publication permission.

**C03 — P1 | The default ticket-link cost is hidden until after the reader clicks.**  
**Status:** open — re-verified; unchanged.  
**Routes:** station results.  
**Evidence:** the default link mode is still the seller's blank search page. The destination row still says "Tickets"; the explanation that the reader must enter the journey is still `#linkNote` inside the initially closed "How these prices were calculated" `<details>`, and the affiliate disclosure is still in that same closed block. The publish checklist requires affiliate disclosure to be visible above the click. What has changed around it: the privacy page now names whether links are tracked and whether an affiliate network is configured, generated from the build rather than from prose, and the build refuses a tracked build with no disclosure.  
**Impact:** a user can reasonably infer that "Tickets" opens the row's journey, but arrives at a generic seller page with nothing pre-filled.  
**Action:** put a concise, row-adjacent explanation of the blank search before the action; if tracking is enabled, show the commission disclosure before the first ticket action (and wherever the publishing terms require it). Keep technical detail in the accordion.

**C04 — P1 | The timetable promise is not conditional on the timetable actually being present, and date basis is buried.**  
**Status:** open, narrowed — the per-row and per-page date facts are now stated; the page's opening sentence still is not.  
**Routes:** station results, especially prices-only and undated-timetable builds.  
**Evidence:** the static intro still promises "the fastest journey time and the number of changes" whether or not a timetable was loaded, and the script still removes the Time and Changes columns without revising that sentence. New since the first pass, and real: a freshness line states the timetable's own service window ("Times are from a timetable covering 21 September 2026 to 11 December 2026, which includes today"), and every row says which absence it is. The undated-schedule warning — that every schedule was read, including changed plans and Sunday services, and that the times are typical rather than date-specific — is still inside the closed methodology disclosure.  
**Impact:** the route can still describe data it does not show; and a reader relying on an undated schedule still has to open a disclosure to learn that it is indicative.  
**Action:** branch the introduction on timetable availability, and move the dated/undated basis next to the times rather than into the accordion.

**C08 — P1 | Fare conditions are not always clear enough at the decision point.**  
**Status:** open, narrowed — the general description is now beside the price; the validity text behind it is still not shown.  
**Routes:** station results, all ticket modes.  
**Evidence:** the row now states the condition in a sentence ("Restricted fare — check seller conditions", then the restriction description) and folds the codes into a "Feed record" disclosure, which is a real improvement over a bare code. The feed's restriction header still carries `desc_out` and `desc_rtn` — the outward and return validity text — and neither string appears anywhere in the builder or the page. Where the feed cannot explain a condition the page still falls back to "check the seller's conditions", which is honest but is not a decoded rule.  
**Impact:** readers may see a general description without the actual outward/return validity and compare prices as if the tickets were interchangeable.  
**Action:** surface a reader-facing summary of the material validity when the feed provides it; retain codes as secondary audit detail. Where the feed cannot explain a condition, say so plainly rather than implying "check seller" is a decoded rule.

### P2 — Significant usability, coverage, and accessibility issues

**C27 — P2 | The chooser requires a known station name or a code prefix.** *(partly addressed)*  
**Status:** open, narrowed — the limitation is now stated on the page; the capability gap is unchanged.  
**Routes:** full-build root chooser.  
**Evidence:** matching is by name substring or three-letter code prefix, and the first 40 matches are ranked by number of destinations. `PRODUCT.md` correctly notes that the fares location records contain no coordinates or region. New since the first pass: the chooser says what its order is and is not — "Ordered by how many destinations this download prices from each station — not by how busy it is, and not by how near it is" — and a no-match names the three-letter code route, so a reader is no longer left guessing what a code is for. No geographic lookup exists, and the audit still holds that "nearest" is not derivable from this feed.  
**Impact:** a first-time traveller who knows where they live but not the official station name or code still has no natural way to choose an origin; a high destination count is not a "near me" signal.  
**Action:** keep the stated limitation, and treat an opt-in geographic lookup as a separate decision with a named, reviewed data source and a manual-search fallback — not as an inference from this feed.
